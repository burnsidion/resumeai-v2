# Tailoring Contracts

## Purpose and status

This document defines the MVP contract for truthful, AI-assisted resume
tailoring. It is the source of truth for the boundaries between source-document
interpretation, role analysis, a proposed working copy, and a future finalized
artifact.

It deliberately does not select a parser, model, prompt, deployment platform,
or PDF renderer. Those choices must implement this contract rather than change
it implicitly.

## Authoritative source and derived records

The uploaded base-resume PDF is the authoritative source document. It remains
private and immutable.

Everything below is derived from that exact document identity:

```text
immutable base PDF
  -> machine-generated interpretation
  -> role analysis
  -> machine-generated working-copy proposal
  -> explicit user acceptance
  -> later deterministic finalized PDF
```

An interpretation is machine-generated, even when extraction succeeds. It must
never be represented as user-verified unless the user explicitly confirms it.
An AI proposal is a reviewable working copy, not a modification of the source
PDF or an accepted resume.

Each derived record must remain tied to the immutable source-resume hash and
the version metadata already owned by the `resume_interpretations` and
`working_copies` tables.

## Canonical interpreted-resume contract

An interpretation has two layers: source blocks and logical sections.

### Source blocks

A source block is an immutable, verbatim extraction fragment with a stable
identifier within one interpretation. It contains:

- an ID generated by the interpreter;
- extracted text;
- page number when known, otherwise `null`;
- deterministic extraction order; and
- a classification useful for interpretation, such as contact, heading,
  position metadata, bullet, paragraph, or other.

Source blocks are evidence anchors, not user-facing layout instructions. A
parser may be incomplete or uncertain; uncertain parsing must not become a
verified fact merely because it has a source-block ID.

### Logical sections

The interpretation organizes supported blocks into existing logical sections,
such as summary, experience, education, skills, projects, certifications, or
other source-present sections. Each section preserves:

- its stable ID;
- the source heading text when one exists;
- its existing logical section kind;
- source-backed entries and items; and
- evidence references to one or more source blocks.

For MVP, these logical sections and their list types are the maximum structural
authority available to tailoring. The model may not create a new section,
heading, summary, list type, or presentation instruction. It may only rewrite,
omit, or reorder source-backed text within an existing logical section or list.

This is a content contract. It does not promise that an arbitrary PDF's visual
layout, columns, or typography can be recovered from extraction.

## Evidence and protected facts

Every factual claim in an analysis or proposed working copy must reference one
or more source blocks from the exact interpretation used for the request.
The server supplies the permitted source-block IDs; the provider may reference
only those IDs.

The following are protected facts:

- name and contact details;
- employers, clients, job titles, and employment dates;
- schools, degrees, certifications, and licenses;
- skills, technologies, projects, awards, and publications;
- numerical metrics and other measurable outcomes.

Protected facts may be reused or emphasized only when supported by source
evidence. They may not be invented, changed, or inferred from the job
description. Contact details should be preserved deterministically by the
server and excluded from provider input whenever they are not needed.

## Separate AI contracts

### Role analysis

Role analysis compares the saved job description with the interpreted source
resume. It returns structured, evidence-backed findings only:

- supported relevant strengths;
- source-backed opportunities to emphasize, reorder, or rewrite;
- honest gaps where no source support exists; and
- recommended content changes with evidence references.

Analysis does not return a complete resume and does not decide a persistence or
lifecycle state. A gap remains a gap; it is not a request for the model to fill
it with a plausible claim.

### Working-copy proposal

The working-copy proposal is a complete, renderable representation of the
existing logical resume sections. It may:

- rewrite source-backed wording for clarity or role relevance;
- reorder items inside an existing section or list; and
- omit less-relevant source-backed items.

It may not:

- add employers, titles, dates, credentials, skills, metrics, or experience;
- create, remove, rename, or convert logical sections or list types;
- choose fonts, margins, columns, colors, spacing, page breaks, or other
  presentation behavior; or
- choose database identifiers, storage keys, state, or provider metadata.

Every changed item carries source evidence. The server, not the provider,
assigns persistence identity, provenance metadata, hashes, and lifecycle state.

### Change summary

The change summary explains material edits in plain language. Each entry has:

- a change kind: rewritten, reordered, omitted, or unchanged;
- the relevant section or item ID;
- a concise user-facing explanation; and
- internal source-evidence references.

The user-facing review may show the explanation but must not expose parser
internals or source-block IDs. Individual keep/revert actions are outside MVP;
the user accepts, requests revision of, or discards the complete proposal.

## Deterministic validation

Structured output is necessary but insufficient. Before a provider result is
shown or persisted, the server must:

1. Validate the response against the relevant runtime schema.
2. Verify every referenced section, item, and source block belongs to the exact
   authorized interpretation.
3. Reject unknown IDs, unsupported section types, and provider-controlled
   identity, storage, or lifecycle values.
4. Preserve protected facts or require valid source evidence for their reuse.
5. Reject deterministically detectable unsupported employers, titles, dates,
   credentials, skills, and numerical claims.
6. Validate the complete working-copy shape, change summary, hashes, and
   provenance before persistence.

Deterministic validation cannot prove every natural-language paraphrase is
truthful. The MVP defense is layered: constrained source input, structured
output, evidence checks, deterministic rejection, clear machine-generated
labeling, and explicit user review.

## Privacy and provider boundaries

Provider requests receive only the minimum structured content necessary for
analysis or rewriting. They do not receive raw PDFs, Supabase credentials,
storage keys, database IDs, application ownership identifiers, or contact
details that can be preserved without model involvement.

The provider credential remains private server configuration. Provider response
storage must be explicitly disabled where the selected API supports that
control. Provider conversations are not ResumAI's system of record; product
state is stored only through the approved server, repository, and RLS
boundaries.

Provider errors, raw messages, and provider-specific response structures remain
server-side. Browser-facing failures use stable, sanitized application codes.

## Tailoring-request coordination

A client-side disabled button is helpful but cannot prevent duplicate requests
from separate tabs or retries. A unique working-copy row prevents duplicate
persisted proposals, but it does not prevent duplicate provider calls before
persistence.

The recommended MVP design is one durable current tailoring-operation record
per application. It is not an AI history table. Its narrow responsibility is to
reserve an in-progress request, prevent concurrent provider calls, expose a
recoverable processing state, and be cleared or completed after a terminal
outcome. It requires an explicit schema decision before OWL-50 implementation.

## Evaluation fixtures

Committed fixtures must be synthetic and safe for source control. They must
not contain a real person's resume, contact information, employer history, job
description, application data, provider response, or credential.

The fixture set covers:

- a source interpretation with stable blocks and existing sections;
- a compatible job description;
- valid source-backed analysis and working-copy examples;
- an unknown-evidence example; and
- an unsupported-claim example.

Later parser, provider, and orchestration tests must use these or similarly
safe fixtures. Routine CI must not call a live AI provider.

## Deferred decisions

The following are intentionally outside this contract:

- parser and model selection;
- prompt wording;
- deployment/runtime selection;
- final PDF visual design;
- deterministic renderer implementation; and
- full revision history or line-by-line approval.

The later renderer will use a conservative ResumAI-owned template with
selectable text and stable layout rules. It will not attempt to edit an
arbitrary uploaded PDF in place, and AI will not control its presentation.
